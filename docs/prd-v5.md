## 1. Executive Summary

**Смена скоупа.** PRD v1–v4 управляли только сайтом `Personal_Projects.github.io`. v5 расширяет границы документа до **всей системы портфолио**: сайт + репозитории проектов (root `00 portfolio/`) + GitHub-профиль (`NikitaBoyarkin/`) + CV (`cv/`) + дистрибуция. Обоснование: связывающее ограничение живёт на стыке этих поверхностей, а не внутри сайта.

**Анализ (2026-09-16, fan-out 3 субагентов).** Субстанция сильная: Топ-10 репо (posthog-saas-analytics, volta-banking, ab_test, sql-analytics-case-study, churn-prediction, causal-uplift, supabase-product-analytics, telegram_bot, social-network-analytics, rfm) несут senior-grade методологию (A/A-калибровка, CUPED, leakage-free ML, golden-тесты SQL, ~97% покрытие). Сайт методологически зрелый (15 проектов, 24 поста, PostHog, Lighthouse-гейты, 4 PRD). **Но охват и доверие не доработаны:**

1. **Красные флаги доверия.** Флагманский кейс на главной указывал на **приватный** `posthog` (также приватны `supabase`, `streamlit`) — **16.09 флагман переключён на публичный `volta-banking`** (REQ-058, as-built); приватные репо остаются приватными. Карточка `bot` на сайте ссылается на **репо-заглушку** `telegram_bot_public` вместо сильного `telegram_bot`. Три репо в профиле пустые (`propensity`, `telegram_bot_public`, `funnel`). Имя `аctivation-funnel` содержит кириллическую `а` — ломает URL. У `airflow` код и PRD живые, но README пуст.
2. **Охват ≈ 0.** 54 уник./90д, LinkedIn ≈ 0, реферер — GitHub. Контент-каденс формально есть (v4 REQ-051), но каналы не управляются (Q8 v4 остался открытым).
3. **Карьерный разрыв.** CV заявляет «4+ года опыта», но раздела «Опыт работы» нет — только синтетические кейсы. PhD по психологии труда не используется как дифференциатор.

**Решение — два контура:**
- **Phase 11 (P0-спринт, ~2 недели): доверие и консолидация.** Убрать красные флаги: открыть флагман, заархивировать мёртвое, починить ссылки сайта, ре-курировать линейку проектов.
- **Phase 12 (90-дневный луп): дистрибуция и карьера.** Управляемые каналы (LinkedIn + hh.ru + GitHub-профиль) с UTM, ревизия CV, north-star дашборд «контакты рекрутеров/мес».

**Ожидаемый эффект:** каждый клик по портфолио ведёт в проверяемый публичный артефакт (0 битых путей), трафик из не-GitHub источников, северная звезда «контакты рекрутеров/мес» измерима и растёт.

## 3. Goals & Success Metrics

### Goal 13: Доверие системы (P0)
- **Описание:** каждый путь проверки из портфолио ведёт в публичный, непустой, работающий артефакт. Ноль красных флагов F1–F7.
- **Метрика:** доля кликабельных путей (карточка проекта → репо/демо), ведущих в непустой публичный репо; число пустых/заглушечных репо в профиле.
- **Baseline:** флагман указывал на приватный репо (переключён 16.09), 1 ссылка на заглушку, 3 пустых репо, 1 сломанное имя.
- **Target:** флагман публичен, 0 пустых репо в профиле, 100% карточек ведут в непустой репо, 0 битых внутренних ссылок (`make check` зелёный). Приватные репо допустимы, если не в featured-позиции.
- **Срок:** конец Phase 11 (2 недели).

### Goal 14: Контакты рекрутеров/мес (North Star)
- **Описание:** число инициатив контакта от рекрутеров/нанимающих в месяц — прямая цель профиля (совпадает с `NikitaBoyarkin/PLAN.md`).
- **Метрика:** контакт-инициативы/мес (Telegram/LinkedIn/GitHub/email) с атрибуцией по источнику.
- **Baseline:** ~1/мес (3 за 90д, только GitHub-реферер).
- **Target:** ≥2/мес к Checkpoint 9; ≥4/мес к концу 90д при работающем охвате.
- **Срок:** 90д (Phase 12).
- **Метод:** PostHog funnel + ручной лог контактов по каналам (REQ-068).

### Goal 15: Охват/дистрибуция
- **Описание:** рост трафика из управляемых каналов до порога значимости конверсионных метрик.
- **Метрика:** уник. визиты/90д по источникам (utm_source); доля трафика не из GitHub.
- **Baseline:** 54 уник./90д, GitHub-реферер доминирует.
- **Target:** ≥100 уник./90д суммарно; ≥30% трафика из не-GitHub источников (LinkedIn/hh.ru); 0 визитов с hh.ru → ≥1.
- **Срок:** 90д.

### Goal 16: Глубина проверки
- **Описание:** рекрутер, дошедший до featured-проекта, открывает репо/демо.
- **Метрика:** доля визитов, дошедших до страницы проекта, с последующим переходом в репо/демо (funnel главная → /projects/<slug>/ → github/demo).
- **Baseline:** фаннел «Рекрутер» существует (v1), целевую долю зафиксировать в Phase 11.
- **Target:** ≥30% посетителей страницы проекта переходят в репо/демо.
- **Срок:** 90д.

## 4. User Stories

### Story 13: Рекрутер — GitHub-профиль
**As a** рекрутер, открывающий профиль из резюме/отклика, **I want to** за 10 секунд увидеть позиционирование, CV-CTA и 3–5 флагманских репо без пустых/приватных заглушек, **So that I can** решить, звать ли на интервью.

**Acceptance Criteria:**
- [ ] README профиля: tagline, 3 кирпича (эксперименты / lifecycle / delivery), «Download CV» выше фолда (REQ-062)
- [ ] В топе профиля — featured-проекты (не игры) (REQ-066)
- [ ] Клик по любому флагману открывает непустой публичный репо (Goal 13)
- [ ] Рекрутер не встречает пустых репо (F4 устранён)

**Dependencies:** REQ-058…060, REQ-062, REQ-066

### Story 14: Нанимающий — проверка флагмана
**As a** нанимающий/тимлид, **I want to** открыть флагманский кейс (Volta) из главной сайта и увидеть код, данные и тесты, **So that I can** проверить методологию, а не поверить на слово.

**Acceptance Criteria:**
- [ ] `volta-banking` публичен, README уровня case-study, воспроизводим (REQ-058)
- [ ] Featured-карточка на главной ведёт на публичный репо (не `posthog`)
- [ ] README репо воспроизводим: одна команда → отчёт/дашборд
- [ ] CI/tests зелёные

**Dependencies:** REQ-058

### Story 15: Владелец — управляемый охват
**As a** владелец портфолио, **I want to** знать, какой канал даёт визиты и контакты, **So that I can** фокусировать усилия на одном-двух каналах.

**Acceptance Criteria:**
- [ ] Все исходящие публикации несут UTM (utm_source/medium/campaign)
- [ ] North-star дашборд показывает контакты/мес по источникам (REQ-068)
- [ ] Еженедельный ревью-ритуал (v4 REQ-050) дополнен источником контакта
- [ ] Решение по фокусу канала принято на 30-й день Phase 12 (по UTM-данным)

**Dependencies:** REQ-064, REQ-065, REQ-068

## 6. Non-Functional Requirements

### Security
- **Перед любой публикацией репо (REQ-058/059):** scrub-проход — grep по API-ключам, токенам, паролям, реальным данным; `.env`/`.env.example` без секретов; `git log` не содержит секретов в истории (при необходимости — пересоздание репо, а не `git filter-branch`).
- Сайт: без новых PII-поверхностей (v4 §6 сохраняется).

### Performance
- Правки сайта не роняют Lighthouse-гейты (v4 §6): LCP < 2.5s, INP < 200ms, CLS < 0.1.
- CLS `/projects/cohort/` — исправить (REQ-063).

### Reliability
- `make check` зелёный после каждой правки сайта (внутренние ссылки + дрейф метрик).
- Публикация репо не ломает воспроизводимость: CI зелёный без секретов.

### Scalability
- Контент-коллекции build-time; рост постов не требует архитектурных изменений (v4 §6).
- Ре-курация линейки (REQ-061) — аддитивна, без новых роутов.

### Operations
- Публикация приватного репо — операция с подтверждением: чек-лист scrub перед push (см. Security).
- Ревью-ритуал (v4 REQ-050) продлевается на north-star дашборд (REQ-068).
